# 手動チェックリスト

自動テストで担保**できない**確認だけをここに列挙する。ここに無い項目は自動テストの
担当であり、手動で確認する必要はない (層の定義 T1〜T6 と自動化戦略は docs/TESTING.md §1)。
節には 2 種類あり、どちらなのかを節ごとに書いてある:

- **自動化できないから人が見る** (§1 / §3 / §4 / §5 / §9 の見た目)
- **一次の網は自動で、人は「自動と実機の差」だけを見る** (§2 / §6 / §7 / §8)

**「やってみたが駄目だった」と「やっていない」は区別して書く。**区別しないと、
次に読む人が同じ道を最初から歩く。自動化を試みて検出力を示せず見送った項目は、
その旨と参照先を項目の側に書いてある。

リリース前、および Picker / オーバーレイ / manifest に触れた変更の後に実施する。
ホストは 3 つある (`UiaTrigger.App.WinUI` / `.Wpf` / `.WinForms`)。断りのない項目は
3 つとも見る。変種ごとに違う項目は §4.3 で分けてある。**§9 (監視のショーケース) だけは
`App.WinUI` 専用**である — 意図された非対称なので (docs/DESIGN.md §12)、
3 ホストで見ようとしないこと。

## 前提環境

物理入力と DPI スケーリングが絡むため、**擬似入力を使わず実機の物理デバイスで**確認する。
以下の 2 環境で行う。片方だけで済ませると、もう片方でしか出ない不具合を一度も
見ていないことになる (どちらの環境にも「そちらでしか出ない不具合」の実績がある):

- [ ] 通常環境 (100% スケール、ローカルコンソール)
- [ ] **高 DPI 環境 (4K / 175% スケール、RDP セッション)**
      ← ホイールバグが顕在化した環境 (docs/TESTING.md §4)

> **確認は「発行物」で行うこと。**`bin/` のホストは **AOT ではない**ので、
> **AOT でしか出ない不具合が原理的に出ない** — 「`GridSplitter` が動かない」(A23) が
> この層の実例である (docs/DESIGN.md §12)。zip か `publish/` を使う。

## §1 物理マウスホイールによるスクロール

自動化不可の理由: `WM_MOUSEWHEEL` の配送はフォーカス + スクリーン座標のヒットテストに
依存し、擬似入力では実際の配送経路を再現できない (誤った結論を導いた実績がある —
docs/TESTING.md §4)。真因が DPI 宣言である以上 **100% で緑でも 175% を保証しない**ので、
ここは今でも人が一次の網である。

- [ ] ピッカーの要素ツリー (TreeView) が物理ホイールでスクロールする
- [ ] ピッカーのプロパティ一覧 (ListView) が物理ホイールでスクロールする
- [ ] MainWindow のトリガー一覧が物理ホイールでスクロールする
- [ ] 上記を **4K / 175% / RDP** 環境でも確認する

> 失敗した場合、まず T2 (DPI 認識 / マージ済み manifest — CI の `build-and-test` ジョブ) の
> 結果を確認すること。そちらが緑なら DPI 認識以外に原因がある。

> **例外: オーバーレイだけを触った変更では、この節は再実施しなくてよい。**
> ここで見るのは**ピッカー自身の `TreeView` / `ListView` とホストの一覧**であり、
> オーバーレイは**対象アプリの上に出る別の窓**なので、その 3 つのホイール経路に入らない。
> 枠の窓は `WS_EX_TRANSPARENT` を持ち、ヒットテストを邪魔しない側に居る
> (docs/DESIGN.md §10)。**オーバーレイ以外に触った変更ではこの例外は使えない。**

## §2 低レベルキーボードフックの副作用

**一次の網は自動である** (T5 = `tests/UiaTrigger.Input.Tests` — docs/TESTING.md §1 / §3)。
「他アプリの内部状態は観測できない」は成り立たない — 対象アプリは自分たちのもので、
キャレット位置を stdin で報告させられる。

**人が見る理由 (補助)**: 合成入力が物理入力と違う点は 3 つあり、そこだけは自動で潰せない。
**注入ビットが立つ** (`HookProc` がそれを読まないことは `HookPolicyTests` が固定している) /
**UIPI** (より高い整合性レベルへは撃てない) / **デバイスとドライバの層を通らない**。

- [ ] **フックのハンドルそのものが漏れていないこと**
      — 上の自動テストが固定しているのは「閉じたピッカーが二度と枠を出さない」ことであって、
      `UnhookWindowsHookEx` が呼ばれたことでは**ない**。枠を出す経路は閉じるときに 3 つとも
      先に切れるので、フックの解除は外から見える差を作らない (実測 — docs/TESTING.md §3 の K3)。
      ここは人が見るしかない
- [ ] ピッカーが異常終了した場合でもフックが残らない
      — ピッカーを開いたまま `Stop-Process -Name UiaTrigger.App.WinUI -Force` で落とし、
      他アプリで ←/→ が普通に効き入力が詰まらないこと
      (OS がフックを掃除するので、これは回帰の網ではなく**事実の確認**である)

## §3 オーバーレイの見た目と操作性

自動化不可の理由: ピクセル単位の正しさは T1 のスナップショットテストが担保するが、
「見やすいか」「押しやすいか」は人間の判断。窓の構造 (枠とアイコンの 2 枚) と
その不変条件は docs/DESIGN.md §10 が正である。

- [ ] 赤枠が選択要素にぴったり重なる (ずれていない)
- [ ] 確定アイコン (✓) の位置が枠の右上として自然で、押しやすい
- [ ] 枠部分がクリックスルーになっており、下のアプリを操作できる。
      **必ず不透明な枠線の上を押すこと** — レイヤードウィンドウのヒットテストは
      ピクセルごとのアルファで決まるので、**透明な内側は構造がどうであれ元から通る**
      (docs/DESIGN.md §10)。内側で確認しても検出力が無く、壊れていても長く緑に見える
      (この項目はまさにその形で壊れたまま緑が続いた実績がある)。
      一次の網は T5 の `OverlayClickTests` (M1 — docs/TESTING.md §3) なので、
      ここは合成入力と実マウスの差を見る**補助**である
- [ ] アイコン部分だけがクリックを受け取る (押すと確定する)。
      **自動の網が 1 つも無い唯一の項目である** (M2 — docs/TESTING.md §3。自動化は
      試みたうえで検出力を示せず見送られている。「やっていない」のではない)。
      T4 の `OnlyTheFrame_IsTransparentToHitTesting` は**原因のほう (拡張スタイル) しか
      固定していない** — 「押したら確定した」を見ているテストは無く、
      次に押せなくなったら落ちるのはこの行だけである。
      ← 上と**逆向きの壊れ方**なので一緒に見ること。「枠が塞ぐ」と「アイコンが反応しない」は
      症状が似ていて原因が逆で、別々の窓の `WS_EX_TRANSPARENT` の有無 = **1 語の変更で入れ替わる**
- [ ] **←/→ で重なりを切り替えたとき、枠とアイコンが一緒に動く**
      ← **「枠だけ動いてアイコンが取り残される」は 1 窓なら原理的に起こらない —
      窓が 2 枚だから起こりうる壊れ方である。**T1 が固定しているのは
      **静止した**座標だけなので、追従の同期はここでしか見ていない
- [ ] **ピッカーを閉じると枠とアイコンが両方消える**
      ← 同じ理由。`WM_DESTROY` で `PostQuitMessage` を投げるのは**枠のときだけ**で、
      終了は**アイコンを先に**壊す (docs/DESIGN.md §10)。どちらの順序を間違えても
      **片方の窓が画面に居座る**が、例外は出ない
- [ ] 高 DPI 環境でも枠の太さ・アイコンサイズが破綻しない (175% では枠 3→5px /
      アイコン 20→36px)。見るのは「要素に対して細すぎ・小さすぎないか」と
      「大きすぎて要素を潰していないか」の両方
- [ ] **100% でも ✓ の字形が破綻していない。**寸法は 96 DPI では 3 / 20 / 10 / 4 / 6
      (T1 が絶対値で固定) だが、チェックマークは**正規化座標**で描かれるので、
      字形は寸法とは別に見る
- [ ] **アイコンより小さい要素 (チェックボックス・スピンボタン等) の見た目。**
      枠は最低アイコン 1 個分まで広げられるので、**要素より大きい枠**が付く
      (175% では論理 20px 未満の要素が該当する)。当たり判定は「広げたあとの枠」の右上に
      揃えてあるので、**見えているアイコンは全面が押せる**はずである (docs/DESIGN.md §10) —
      そこも一緒に確認する

## §4 ローカライズの見た目

自動化不可の理由: キーの網羅性・翻訳漏れは単体テストが担保するが (docs/TESTING.md §1 の T1)、
**訳文が長くなってレイアウトが破綻していないか**は目視でしか判断できない。

- [ ] OS の表示言語が **English** のとき、ピッカー / MainWindow のすべての文字列が英語で表示される
- [ ] OS の表示言語が **日本語** のとき、すべての文字列が日本語で表示される
- [ ] 上記いずれでも**ボタン・ラベルの文字切れ、折返し、はみ出しが無い**
      (条件種別の説明文など、英語のほうが長くなる箇所に注意)
- [ ] 未対応言語 (例: 中国語) の OS で英語にフォールバックする

### §4.1 `x:Uid` の解決 — 一次の網は自動である

`.resw` が resources.pri に入ることは発行出力の検査が、**MRT Core が実行時にその文字列を
実際に画面へ流し込むこと**は発行レイアウトを起動する T4 が固定している —
ピッカーの窓 (ラベル・ウィンドウタイトル・リソースマップ名・`GetString` 経路) は
`PublishedResourceTests`、ホストの MainWindow (タイトル・全ボタン・ラベル・起動直後の状態欄) は
`HostPublishedResourceTests`。どちらも en-US / ja-JP の両方を**リポジトリのリソースファイルの
値との一致**で照合し (解決失敗の症状は経路で違う — `x:Uid` は空・`GetString` はキー名 —
ので、値と比べないと両方は捕まらない)、キーの被覆そのもの (「見る」か「理由付きで見ない」か)
も両方向で固定している。CI では `aot` ジョブがブロッキングで回す (docs/TESTING.md §1)。

残る手動項目: **なし**。ただし次は網に**入っていない** (「できない」ではなく「やっていない」):

- 操作しないと出ないホストの文字列 (保存後の件数・監視の開始/停止・まとめの結果) は
  値を照合していない。理由と回収の道は `HostPublishedResourceTests` の除外リストにある
- `App.WinForms` の MainWindow は実行時照合していない
  (resx 経路の代表を WPF に置く判断 — `PickerHostProfile.AllNames`)

### §4.2 コントロール型の表示名と安定名

一次の網は自動である: プロパティ一覧の `ControlType` 行が表示名と安定名の対で出ることは
T1 (`Properties_ShowBothNamesForTheControlType`) と T4
(`CommitTests.TheTreeAndThePropertyList_NameTheControlTypeTheWayTheTargetDoes` —
対象要素の `LocalizedControlType` をテスト側 UIA で**独立に**読み、行を書式ごと厳密比較する)
が、ツリーの行が対象アプリのプロバイダーの言う表示名で出ることも同じ T4 が、
確定した `DisplayName` が安定名から作られることは T1 (`ControlTypeNameTests`) と
T3 (`Record_PutsTheStableNameInTheDisplayName`) が固定している。

- [ ] ピッカーの要素ツリーに出るコントロール型が**対象アプリの言語**になっている
      (日本語の対象アプリなら「ボタン」等)。対象アプリを別の言語で起動し直しても
      保存済みの定義 (`DisplayName`) が変わらないことも一緒に見る
      ← **実言語での確認だけが残る。自動化を調べて、検出力のある形が無いと分かった項目である**
      (「やっていない」のではない)。表示名を出すのは対象アプリ側のプロバイダーで
      (docs/DESIGN.md L6)、対象アプリ (TestTarget) に言語を切り替える口が無く、
      CI ランナーの OS 表示言語も切り替えられない。口を足してアプリに期待値まで出させると
      「アプリが言った値をアプリに確かめる」円環になり検出力が無い
      (`TestTarget.Wpf/Peers.cs` の既存判断と同じ形)。自動の網は代わりに
      **言語非依存の対の一貫性** (表示名 ≠ 安定名の序数比較・独立読みとの一致 —
      `ControlTypeNameScenarioTests` と上記 T4) を固定しており、人が見るのは
      「別言語の環境で実際にその言葉になる」ことだけである

### §4.3 View に残した経路

自動化可否は **View によって違う**:

| View | T1 から参照 | ここに残る理由 |
|---|---|---|
| WinUI3 | **できない** | WinUI3 / x64 / WindowsAppSDK。T1 がまるごと引きずられる (docs/DESIGN.md §12) |
| WPF | できる | **コンテナの実体化にはウィンドウの表示が要る** (下記) |
| Windows Forms | できる | 仮想化が無く、ウィンドウを出さなくてもノードは存在する → **ほぼ自動化済み** |

> **実測**: WPF の `ItemContainerGenerator` は `Measure`/`Arrange` でもディスパッチャーの
> 掃き出しでもコンテナを返さず、`Window.Show()` して初めて `TreeViewItem` が生成される。
> 可視のデスクトップを要する検査は T1 の担当ではなく (docs/TESTING.md §1)、
> T4 (`tests/UiaTrigger.Picker.UiTests` — ホストを子プロセスで起動し `--pick-at` で
> ホバー捕捉を起こして UIA から駆動する。擬似入力は使わない) が引き取っている。

#### §4.3.1 3 変種に共通 (それぞれのホストで実施する)

- [ ] **窓が出た瞬間の大きさが 3 変種で揃っている** (ピッカー 1100×700 / エディタ 900×560 /
      ホスト 900×600 — いずれも表示スケールを掛けた大きさ)。**高 DPI の画面で見ること。**
      ← **自動では観測できない項目である** (「やっていない」のではない)。WinUI3 の `Window`
      だけは既定サイズを XAML で宣言できず `AppWindow.ResizeClient` を呼んでおり、
      あれは**物理ピクセルを取る**ので表示スケールを掛け損ねると他の 2 変種の 57% で開く。
      **例外も警告も出ず、ただ小さい。**T1 が見られるのはソースの形だけ
      (`PickerWindowDefaultSizeTests`)、T4 はホストの窓を割り付けの矩形へ**寸法ごと**
      退かすので既定サイズを上書きしてしまう (docs/TESTING.md §1 の 9)
- [ ] ホバー捕捉でチェーンが上から順に展開され、**選択が末端の要素に着く**
- [ ] 行をクリック / ダブルクリックすると**その行の子が全列挙される**
- [ ] ツリーで別の行を選び直すとオーバーレイの枠とプロパティ一覧が追随する
      (差し替え中の抑止が効きすぎていないこと)
- [ ] 選択モード中の ←/→ で重なり切替ができる
- [ ] ビューを Raw / Control / Content と切り替えても選択が保たれる
- [ ] **対象ウィンドウを動かしてから別の行を選ぶと、枠が現在の位置に出る**
- [ ] 赤枠右上の確定アイコンにカーソルを重ねても、**待ちカーソル (砂時計) にならない**
      ← 原因の側は自動 (`OverlayTests.TheOverlayWindowClass_RegistersACursor`) だが、
      実際にどう描かれるかは実マウスを動かさないと見られない。**補助として残す**
- [ ] **区切りを掴んで動かせる**。境界は 2 つ — **ツリーとプロパティ一覧** (上段の左右) と
      **上段と条件欄** (上下。条件欄は窓の全幅)。窓を縮めてから、それぞれを広げたり狭めたりする。
      見るのは 3 つ: **カーソルが境界で変わること** / **どちらの側も潰し切れないこと**
      (最小寸法で止まる) / **区切りに Tab で止まり、←/→ (上下の区切りは ↑/↓) で動かせること**。
      立っている位置は自動 (`SplitterTests` / T4) だが、**掴めるかどうかは合成入力になるので残る**。
      Windows Forms は元から `SplitContainer` で、開始位置と最小寸法は T1 が見ている。
      **この項目は必ず発行物で確認すること** — WinUI の Sizer の書き戻し (`GridLength`) は
      **AOT 発行でだけ壊れる層**に載っており (docs/DESIGN.md §12)、`bin/` では原理的に出ない
- [ ] **条件欄を縮めても [トリガーを追加] へ辿り着ける** (スクロールで届く)。
      窓を縦に縮めて、条件欄がスクロールして届くことを見る。
      `ScrollViewer` が在っても `Auto` の行がビューポートを中身ぶんに伸ばすと
      **スクロールが一生起きない**形に壊れる (WinUI / WPF)。縮めたときに切れることは
      自動では見ていない — T1 が見ているのは**既定で切れていない**ことと
      **条件欄に上限が渡っていること**までである。
      Windows Forms は元から `SplitContainer` + `AutoScroll` なのでこの形にならない
- [ ] **既存トリガーを読み込むと条件欄がその値で埋まる**。見るのは 3 つ:
      **id・発火契機・プロパティ・演算子・値がすべて入っていること** /
      **ホバー追随のトグルが切れていること** (切れていないと、マウスが要素の上に静止しただけで
      編集対象が差し替わる — docs/DESIGN.md §4 の `ShowDraft`) /
      **何も変えずに [トリガーを追加] を押すとファイルが変わらないこと**。
      往復そのものは T1 が見ている (`ShowDraftThenReadDraft_RoundTripsEveryField`)。
      **WinUI だけは T1 から組み立てられないので、実物で見るのはここと T4 の編集経路である**

#### §4.3.2 WinUI3 固有

T1 の `FakePickerView` は同期で動き、行の「コンテナ」を必ず見つける。本物は
`ContainerFromItem` + `UpdateLayout()` へのリトライを持つ別物で、その実体化待ちの経路は
T4 が覆っている。

- [ ] **エディタの「まとめる」行のポーリング間隔の欄 (NumberBox) が行に収まって見える**
      (175% と 100%)。出入り・値の伝搬・文言は自動 (T1 / T4) で、ここは見た目だけである
- [ ] **編集セッションの確定ボタンが「トリガーを更新」で崩れず収まる** (ja/en)。
      文言の解決と差し替わりは T4 (`EditorShowcaseTests`) が見る。ボタン幅は文言で変わるので
      見た目だけが残る
- [ ] **エディタの窓を縮めても下段 (まとめる行〜OK/キャンセル) がスクロールで届く**
      (縦横どちらも)。← **UIA では確かめられない項目である** (「やっていない」のではない)。
      素の ScrollViewer の `ScrollPattern` は extent をビューポートと同値に過小報告し、
      `SetScrollPercent` も実可動域に届かない — 人が動かして動くと確認済みのピッカーの
      条件欄すら同じ数字を返す (実測。docs/DESIGN.md §4)。横方向の到達だけは
      UIA で実測済みなので、見るのは主に縦である
- [ ] **エディタの一覧に横スクロールが出て、複合の長い行を最後まで読める**
      (縦のスクロールは元から効いている)。出るか出ないかは実測済みだが、
      掴んで動かすのは合成入力になるのでここに残る

#### §4.3.3 WPF 固有

コンテナの実体化にウィンドウの表示が要る経路 (§4.3 冒頭の実測) は T4 が引き取っている。
それ以外は T1 (`TriggerPickerWpfWindowTests`) が覆っている。残る手動項目: **なし**。

#### §4.3.4 Windows Forms 固有

**この節は意図的に短い。**仮想化が無くウィンドウを出さなくてもノードが存在するので、

#### §4.3.5 トリガ一覧エディタ

**T4 (`EditorShowcaseTests`) が覆っているのは WinUI ホストだけである。**WPF / Windows Forms の
エディタは `ShowDialog` による本物のモーダルで、UIA の `Invoke()` が**ダイアログが閉じるまで
返らないおそれがある**ため、あちらはここに残る (エディタの設計は docs/DESIGN.md §4)。

**WPF / Windows Forms で人が見ること** (それぞれのホストの [一覧を編集] から):

- [ ] **本物のモーダルであること**。エディタが出ているあいだホストの窓を操作できず、
      エディタは**ホストの中央**に出る (所有者が付いている)
- [ ] [追加] で子ピッカーが開き、**モーダルのエディタの上で操作できる**
      (所有者を付け違えると、入れ子のメッセージループの外に取り残されて反応しなくなる)
- [ ] エディタを閉じると**子ピッカーも一緒に閉じる**。取り残すとオーバーレイの
      低レベルキーボードフックが張られたまま残る — 画面にも例外にも出ない副作用である
- [ ] [ほどく] で複合が句ごとのトリガーに戻り、**複合そのものも一覧に残る**
      (まとめる・ほどくはどちらも足すだけ)。戻ったトリガーは [条件を編集] できる
- [ ] **[条件を編集] で開いた子ピッカーは確定ボタンが「トリガーを更新」で、確定 1 回で閉じる**。
      [追加] で開いたピッカーは「トリガーを追加」のまま開き続ける。
      振る舞いは 3 変種共通の presenter (T1 が固定) だが、**閉じる操作は View 固有**
      (WinForms の `Form.Close` は Dispose する) で、WinUI 以外は T4 が届かないのでここに残る
- [ ] **一覧の行をダブルクリックすると [条件を編集] と同じに動き、子ピッカーが
      前面 + フォーカス付きで開く** (3 変種とも。WinUI 含む)。
      複合の行ではボタンと同じ理由がステータスに出る。一覧の**空白部分**のダブルクリックでは
      何も起きない。← ダブルクリックは合成入力でしか起こせず、UIA にも該当パターンが無いので
      自動化できない (ピッカーの行ダブルクリックと同じ扱い — §4.3.1)。前面に出ることは
      実測済み (docs/DESIGN.md §4 — ハンドラ内で直接開くと WinUI では後ろに出る) だが、
      環境で変わりうるので目視も残す
- [ ] **WPF のエディタも、窓を縮めると下段 (まとめる行〜OK/キャンセル) がスクロールで届く**。
      上限の配線は T1 が縛るが、実際に縮めた画面はここでしか見られない (WinUI 側の
      §4.3.2 の項目と同じ理由)。Windows Forms は Dock がバーを常に確保するので対象外
- [ ] **「まとめる」行のポーリング間隔の欄に値を入れてまとめると、複合の `PollInterval` に入る**
      (真偽はトリガーファイルで見る)。空欄ならファイルに現れない
- [ ] **何も直さずに [複合を更新] を押し、[OK] で保存すると、トリガーファイルが押す前と
      バイト一致する。**式を変えて押す確認だけでは、ポーリング間隔が黙って落ちても
      絞るだけの句が監視側へ裏返っても気付けない。**バイト一致は人にしか見られない** —
      T4 は「立ち下がり通知が乗っていること」までしか見ないためである
- [ ] 式を変えて [複合を更新] を押すと、一覧の**その行が同じ位置で**書き換わり、
      **id は変わらない**。行が末尾へ移ったり、複合がもう 1 件増えたりしない
- [ ] **絞るだけの欄に出るのは句の名前** (`login-1` のような `-N` 付き) であって、
      まとめる前のトリガー id ではない (docs/DESIGN.md C17)。複数句のトリガーを

- [ ] **175% と 100% の両方で**、ボタンの文字が切れず一覧が読める。まとめる行に

**次の 4 つは T4 が見るので、人は見なくてよい**
(`EditorShowcaseTests.CombiningWithTheFallingEdge_ShowsUpInTheUiAndInTheFile_AndStaysUpdatable`。
ただし WinUI ホストだけである — WPF / Windows Forms のエディタは本物のモーダルで
UIA の `Invoke()` が返らないおそれがあるため、**あの 2 変種では下の 4 つも人が見る**):

## §6 ピッカーを複数同時に開く

オーバーレイのウィンドウと低レベルフックは、実際のメッセージループが無いと成立しない —
複数起動で効くのは View ではなく、HWND / フックスレッド ID を鍵にした登録表とフックである
(docs/DESIGN.md §10)。自動は WPF ホストだけで回している — `OverlayController` は
`Picker.Core` に在って 3 変種で同じものなので、変種を増やしても被覆は増えない。
**WinUI ホストは 2 つ目を開くところから手動で見る。**

- [ ] 両方閉じるとフックが 2 つとも外れる (他アプリの ←/→ に干渉しない)
      — 片方ぶんは `AfterThePickerIsClosed_ArrowsShowNoFrame` が見ているが、
      **ハンドルが漏れていないこと自体は外から観測できない** (§2 と同じ理由)
- [ ] **2 枚目を開くと、1 枚目のマウス自動選択が OFF になる。**
      **カーソルはプロセスで 1 つ**なので、調停しないと先に開いていたほうが新しいピッカーの
      マウスに黙って追随し、出していた要素を失う。**確定済みの条件が無事であること**も
      一緒に見る (調停の設計は docs/DESIGN.md §12)
- [ ] **開いたあとで両方の自動選択を手で ON に戻すと、また同じ点を見る (仕様)。**
      調停は「開いた瞬間の一度きり」であって不変条件ではない。
      **ここを「不具合」と読まないために書いてある** — 常に 1 枚だけにするなら調停は
      `SetAutoSelect` の側に要り、他のピッカーの表示も裏返す必要がある
      (= `IPickerView` への追加なので、公開後には入れられない)

## §8 応答しないアプリに対する耐性

**一次の網は自動である。**「『応答しないアプリ』を CI で安定して作れない」は成り立たない —
対象アプリは自分たちのもので stdin のコマンド protocol を持ち、UI スレッドを塞ぐ
`hang <ms>` で**決定的に**作れる (docs/TESTING.md §1 の T3)。耐性の設計は docs/DESIGN.md §3。

- [ ] 停止したアプリのトリガーは未解決になり、復帰後に再解決される
      — **前半は自動化できない。実装がそうなっていないためである。**解決済みのトリガーは
      塞いでも未解決にならない (揺れないという意味では正しい振る舞いなので、未解決を要求する
      テストは書いていない — docs/DESIGN.md §3)。**後半 (復帰) だけ**が
      `AfterAnUnresponsiveSpell_TheAppsOwnTriggerResolvesAgain` (T3) で自動になっている。
      **デバッガでブレークした場合も同じかどうかは人が見るしかない**

### 人が見る理由 (補助)

自動の `hang` は**協調的な停止**である — 対象アプリが自分の UI スレッドを塞ぐモデルであり、
**本当に固まったアプリ (デバッガでブレーク、カーネル待ち、ハングしたドライバ) では、
UIA の呼び出しが返らない層が別にありうる** (相手のメッセージキュー / 他プロセス待ち /
コンポジション)。この差だけが人に残る。

- [ ] デバッガでブレークした対象アプリに対して、上の 2 項目が同じように成り立つ
- [ ] 呼び出し上限時間が効いていること (`UiaSession.GetSupportsTimeoutsAsync()`)。
      **自動テストは両方ともこれを assert しているので、緑なら成立している**

> 「自動化できないから人が見る」と「網は張ったが人でしか見られない差が残る」は別のことである。
> この文書は両者を節ごとに区別して書いてある。

## §9 監視のショーケース — **`App.WinUI` だけ**

一次の網は `MonitorShowcaseTests` / `CompositeShowcaseTests` (T4) である
(それらの assert の置き方には理由がある — テストを弱める前に docs/TESTING.md §2 を読むこと)。
ここに残るのは、自動では見られないもの (見た目・配分・実物の対象アプリでの切り分け) である。
監視を持つのは `UiaTrigger.App.WinUI` だけ — README の "Two asymmetries are deliberate"
が明記する意図された非対称である (docs/DESIGN.md §12)。

> **この自動化が対話デスクトップに要求するのは 4 つである**:
> ウィンドウを実際に作って表示できるデスクトップ / UIA のプロバイダが同じセッションに
> 居ること / 本物の z-order と画面座標 (`ElementFromPoint` が通るため) / 十分な解像度
> (**1600×900 は通り、1024×768 は 4 件落ちる** — docs/TESTING.md §6)。
> **物理入力は要らない** — 駆動は UIA のコントロールパターンだけで足りる。

### 複合条件

**別プロセスを 2 つ立てて確かめること。**同一ウィンドウ内の 2 要素だと、
スロットが割れていても素通りするので何も確かめたことにならない
(スロットの設計は docs/DESIGN.md §4)。

> **対象アプリを選ぶこと。**「ふつうのアプリ 2 つ」でやろうとすると、
> **アプリ側が UIA の `PropertyChanged` を上げなければ永久に鳴らない**。
> 既定ではポーリングしないので、これは不具合ではなく設計の帰結である (docs/DESIGN.md §5)。
> **「鳴らなかった」がライブラリの問題なのか対象アプリの問題なのか切り分けられない対象で
> このチェックをやってはいけない** (電卓がまさにそれである — 下のポーリングの節)。
> そういうアプリだと分かった場合の手当てが `PollInterval` だが、
> **この節はポーリング無しで確かめること** — 複合条件の検査であって、ポーリングの検査ではない。

**確定的に鳴る対象として `tests/UiaTrigger.TestTarget` を使う。**
コンソールサブシステム (`Exe`) なので、**ターミナルを 2 枚開いて直接叩けばよい**。
コマンドを 1 行打つと `ok <verb>` か `err <理由>` が返る。

```
1 枚目> cd tests\UiaTrigger.TestTarget\bin\Release\net10.0-windows
1 枚目> .\UiaTrigger.TestTarget.exe --title target-A
        add-button btnA
        place 620 40 520 700

2 枚目> cd tests\UiaTrigger.TestTarget.Wpf\bin\Release\net10.0-windows
2 枚目> .\UiaTrigger.TestTarget.Wpf.exe --title target-B
        add-button btnB
```

条件を動かすのは `set-text btnA ready` / `set-text btnB done`。終わったら `exit`。

> **`place` を先に打つこと。**既定では 2 つとも (40,40) に 520x1000 で出て**完全に重なる**。
> 記録は座標 (`ElementFromPoint`) を通るので、重なったままだと一方の記録が
> もう一方のタイトルバーを掴む。`place` を持つのは WinForms 側だけである (WPF 側には無い)。
>
> `620 40 520 700` は 1600x900 でも収まる値である (620+520=1140 / 40+700=740)。
> 画面がこれより狭ければ詰めること — はみ出した部分は座標から記録できない。
> 置けたかは `rect btnA` / `rect btnB` で確かめる。**2 つの x 範囲が重ならなければよい。**

> **PowerShell からパイプで流し込まないこと。**PS はネイティブコマンドへのパイプに BOM を
> 付けるので、**最初の 1 行だけ `err unknown command` になる**。手で打つぶんには起きない。

- [ ] **同じ要素**を指すトリガーを 2 件まとめると、要素の数が **3** と出ること
      (**3 = 元の 2 件 + まとまった複合の 1 個。**複合の中でまとまらない退行では 4 —
      同じ要素に購読が 2 本立つと 1 回の変化で 2 回鳴る)。**別々に録った 2 件**で見ること
      (同じ定義を選び直すのでは、まとまって当たり前の経路しか通らない)。
      まとまり自体は T1/T3 が縛っており、ここで見るのは**画面から録った 2 件でもそうなるか**だけである
- [ ] 式の欄に `a || b` のように書いて、片方だけで鳴るようになること
- [ ] **「絞るだけで発火させない条件」に片方の名前を書いてまとめる**
      → **その要素をいくら変えても鳴らず**、もう片方を変えたときだけ鳴ること
      ← 購読はプロパティから作られ演算子を見ないので、ここが壊れると
      「存在を見るだけ」のつもりの条件が発火源のままになる (`Watch` — docs/DESIGN.md §4)
- [ ] `composite-1` と別のトリガーを選んでもう一度まとめられること (入れ子)

### ポーリング

複合条件の検査を「ふつうのアプリ」でやると、対象が `PropertyChanged` を上げない場合に
切り分け不能になる — その事例がそのまま検査になっている節である
(ポーリングの不変条件と意味論は docs/DESIGN.md §5)。

> **ホストにポーリング間隔の欄は無い。これは仕様である** — ピッカーは記録するだけで、
> `PollInterval` はモデル側のプロパティだからである。**UI を探して「見つからないので実施せず」
> としないこと。**手段は 2 つ:
>
> - **`TestHost` から指定する (こちらを推奨)。**`record` に `--poll-interval <秒>` があり、
>   停止時に `診断: ... ポーリング周=N ポーリング読み=M` が出る。
>   **切り分けに要るのはこの数字である**
> - 保存済みの JSON (`%LOCALAPPDATA%\UiaTrigger\triggers.json`) を手で開いて
>   `"PollInterval": "00:00:00.500"` を足す。往復できることは `TriggerJsonTests` が
>   固定しているので、この経路は信用してよい。記録したものはホストの一覧にもそのまま出る

#### (a) 機構が動くこと — **確定的に鳴る対象で**

`tests/UiaTrigger.TestTarget` を使う。起動は複合条件の節と同じ手順でよい。
`TestHost` は zip に入っている。

```
> .\UiaTrigger.TestHost.exe record poll1 --point <x>,<y> --poll-interval 0.5 --on PropertyChanged
> .\UiaTrigger.TestHost.exe monitor --duration 20
```

- [ ] `set-text btnA ready` で**鳴る**こと (ポーリングの有無に関わらず鳴る経路)。
      `set-accessible-name` (通知を上げない変化) で鳴らすほうが厳しい検査になる
- [ ] **そのあと何もしない間、1 件も鳴らないこと** ← **いちばん大事な項目である。**
      ポーリングを足したときに最も起きやすい壊れ方は「動かない」ではなく**毎周期鳴る**で、
      しかもそれは「ちゃんと動いている」ようにしか見えない
- [ ] 停止時の診断で**ポーリング周が 0 でない**こと
      (0 なら上の「鳴らなかった」は何も確かめていない)
- [ ] `--poll-interval` を**付けずに**同じことをすると、**ポーリング周が 0** であること
      (頼まなければ回らない、の目視版 — ネガティブコントロール)

#### (b) 動機の事例 — 電卓

- [ ] 電卓の表示部を記録し、`--poll-interval 0.5` を付けて監視 → 鳴ること
      (電卓は表示部の変化で `PropertyChanged` を上げないので、ポーリング無しでは鳴らない)
- [ ] なお鳴らない場合、**診断のポーリング周と読みを見る**こと。
      両方伸びているなら「ポーリングは回っている / 対象の UIA 値が本当に変わっていない」であり、
      **ライブラリの問題ではない**。0 のままならライブラリ側である
      ← **「鳴らなかったこと」だけを根拠にしない**、という複合条件の節と同じ規律である

### 見た目 (§3 とは別。ここはホストの窓である)

**§3 は「オーバーレイの見た目と操作性」= ピッカーの枠の話であり、ホストの窓を見ていない。**
ログ一覧を持つのはこのホストだけなので、ここに置く。

- [ ] トリガー一覧とログ一覧の**高さの配分**が実用的であること。
      2 つの一覧の間に区切りが在るので、見るのは既定の配分の良し悪しより
      **掴んで動かせること**のほうである
- [ ] ログ行が横に長いとき、水平スクロールで右端まで読めること
- [ ] **100% と 175% の両方で**見ること (前提環境の注記を参照)
