# UiaTrigger テスト戦略と検証哲学

テスト層の定義 (T1〜T6)、横断ルール、合成入力の政策 (K1〜K5 / M1〜M2)、その根拠になった事例、
既知の不安定テスト、ローカル実行の注意の正典である。設計判断そのものは docs/DESIGN.md にある。

## §1 テスト層

GUI 領域の大半は自動化できる。前提は 2 つだけである:

- **(a) 擬似入力を、入力経路そのものの検証に使わない。**
- **(b) 検証ハーネス自身を検証する。**

この 2 つの出どころは §4 の事例である。自動化率の高い順に 5 層 + 手動 1 層で構成する。
**T1〜T6 の記号はこの節が正である。**

| 層 | 何を見る | プロジェクト | CI ジョブ | 扱い |
|---|---|---|---|---|
| T1 | UIA 非依存の純ロジック | `tests/UiaTrigger.Core.Tests` | `build-and-test` | 必須 |
| T2 | 構成・環境の不変条件 | 同上 | `build-and-test` | 必須 |
| T3 | 専用対象アプリへの実 UIA | `tests/UiaTrigger.RealUia.Tests` | `real-uia` | 観測 (`continue-on-error`) |
| T4 | ピッカーの UI 自体を UIA で駆動 | `tests/UiaTrigger.Picker.UiTests` | `picker-ui` | 観測 (`continue-on-error`)。ただし `PublishedResourceTests` / `HostPublishedResourceTests` だけは `aot` ジョブでも回り、そちらは必須 (フィルタは部分一致で両クラスを含む) |
| T5 | 合成入力で最下層から駆動 | `tests/UiaTrigger.Input.Tests` | `input` | 必須 |
| T6 | 手動チェックリスト | docs/MANUAL-CHECKS.md | — | 人 |

このほか CI には `aot` (AOT 発行 + ローカライズの実行検証 + 発行レイアウトでの T4)、
`arm64-build` (ビルドのみ。「建つこと」と「動くこと」を混同しないためジョブ名にも build と書く)、
`lint` (合成入力の 2 本 — §3) がある。

ジョブの分離には理由がある (どれも「同居させると互いを壊す」):

- **T3 と T4 は別ランナー。**どちらも画面に窓を出して座標から要素を掴むので、
  同じデスクトップで同時に走らせると互いの窓を掴む。
- **T5 は T4 と別ランナー。**低レベルフックはグローバルで、撃ったキーは同じデスクトップの
  すべてのプロセスに届く。窓を分けても分離できない。
- T3/T4/T5 は対話セッションを要するため「まず観測 → 安定したら必須化」。T1/T2 は常に必須。

### T1 — UIA 非依存の純ロジック層

条件評価・スコアリング・ビーム探索・経路構築・JSON に加え、GUI 由来のロジックをここへ引き下ろす。

- オーバーレイの描画は純関数 (`OverlayGeometry`)。矩形と DPI から ARGB ピクセルバッファを作る
  副作用の無い関数で、枠・アイコン・チェックマークをピクセル単位で固定する。
  座標はすべて物理ピクセル。**DPI は引数で渡す** — 中で引きにいくと T1 が固定できなくなり、
  T4/T5 の期待矩形も計算できなくなる。
- ピッカーの振る舞いは `TriggerPickerPresenter` として View から分離し、偽物 (`PickerFakes`) で
  検証する。入力検証は `TriggerDraftValidator`。
- ローカライズの回帰: リソースキー集合の一致、条件評価に使う比較文字列が
  `CurrentCulture` に依らず invariant のままであること。
- `UiaTrigger.Picker.Core` (`net10.0-windows` / AnyCPU) へは普通の `ProjectReference` で届く。
  WinUI の View はここから組み立てられない — ウィンドウの実体化が要るものは T4 の担当である。
- **T1 は並列で回る。**並列を切っているのは T3/T4/T5 の 3 プロジェクトだけである
  (§5 (2) の揺れはこの性質と関係している可能性がある)。

主張できる範囲: ロジックの正しさだけ。画面に出さないと再現しないもの・UIA プロバイダー実物の
挙動・入力の配送については何も言えない。

### T2 — 構成・環境の不変条件 (最重要)

**§4 の事例を 1 行で捕まえられたテスト**を置く層。擬似入力は一切使わない。

| テスト | 内容 |
|---|---|
| interop の形 | 手書き `[GeneratedComInterface]` のメソッド数と宣言順 (`InteropShapeTests`)。**1 つ増減するだけで別の vtable スロットを呼ぶ**のに、コンパイルも AOT 発行も通ってしまう |
| DPI 認識 | プロセスが **`PER_MONITOR_AWARE_V2`** であること。これ単体で §4 の事例を初日に検出できる |
| マージ済み manifest | ビルド成果物の `obj/**/Manifests/app.manifest` を XML パースし、`dpiAwareness=PerMonitorV2` / `supportedOS` を確認 (csproj の配線の回帰防止) |
| 座標系の一貫性 | `GetWindowRect` (物理) と UIA `BoundingRectangle` (物理) と Picker が使う座標の一致。**この不一致こそ §4 の真因の手がかりだった** |
| ホスト要件 | ホストが PerMonitorV2 でない場合に実行時チェックが診断 (`UiaSession.CoordinateProblem`) を上げること |
| AOT 発行 | `PublishAot` が警告 0 で通ること |
| AOT + サテライト | AOT 発行後のバイナリを ja-JP で実行し、メッセージが日本語化されること。**AOT でしか露見しない類の問題**なのでここに置く |

### T3 — 専用対象アプリへの実 UIA テスト

対象アプリは 2 つある。差が論点なので、**片方に寄せないこと**:

| プロジェクト | UI | プロバイダー | 残す理由 |
|---|---|---|---|
| `tests/UiaTrigger.TestTarget` | WinForms | MSAA ブリッジ | 起動が速く UIA が安定している。クラス名に可変 token を含むため窓照合の回帰ケースそのものになる |
| `tests/UiaTrigger.TestTarget.Wpf` | WPF | ネイティブ UIA | イベントの届き方も要素の消え方も MSAA ブリッジと違う。切り離された要素の監視継続はこちらでしか観測できない |

- **擬似入力を使わず、stdin のコマンド行で UI を変化させる。**応答は必ず `ok`/`err` の 1 行で
  終わるので、「コマンドが UI に反映され終わった」時点を待ち合わせられる。
- **`hang <ms>` だけは応答を先に返してから塞ぐ。**コマンドループは UI スレッドに居るので、
  その場で眠るとハーネスが応答を待って一緒に固まる。あわせて `Post` / `AwaitResponse` で
  「応答を待たずに送る」経路がある — **塞がっていたことを塞ぎの後に確かめても、
  観測した窓のあいだ塞がっていた証拠にならない。**
- **定義は手で組み立てず、ユーザーと同じ経路 (座標からの記録) で作る。**手で組むと
  「解決側は正しいが記録側が壊れている」組み合わせを永久に見逃す —
  記録と解決の突き合わせが T3 の主眼である。
- **全件を両方の対象アプリで走らせない** (`TargetProfile`)。広げるのは購読スコープ・型変化・
  **ゾンビ検出** (ツリー再構築後に、古い要素の残骸ではなく新しい要素を見ていること —
  `Monitor_AfterTheTreeIsRebuilt_WatchesTheNewElementNotTheZombie`)・ウィンドウ張り替え・
  表示名など、**プロバイダーの挙動そのものが論点**のものだけ。実行時間と flake を倍にして
  得るものが無いからである。能力差は `Assert.SkipUnless` で**理由付きで**スキップする。
- ハーネス自身の検証: 記録した経路の末尾が本当に狙ったコントロールかを記録のたびに assert する /
  テストプロセスが PerMonitorV2 であることを assert してから記録する /
  各シナリオに「わざと壊した条件では発火しない」対を置く /
  ウィンドウはテストごとに一意なタイトルで起動し定義をそのタイトルに固定する
  (残存プロセスを取り違えたまま通ったテストは、通っていないのと同じ)。

主張できる範囲: 実プロバイダーとの突き合わせ。ただし開発機とランナーの環境差は消せない —
**この機械で緑になっても「壊れる状況が起きなかった」を意味しうる** (§5 (3) が実例である)。

### T4 — ピッカーの UI 自体を UIA で駆動

このライブラリは UIA クライアントなので、自分の GUI を自分で操作できる。ただし擬似入力は使わず、
**UIA のコントロールパターン (`Invoke`/`ExpandCollapse`/`SelectionItem`/`Value`) で駆動**する。
「入力がどこへ届くか」ではなく「ロジックと表示が正しいか」を問う。
`WH_KEYBOARD_LL` も `WM_NCHITTEST` も一度も通らないので、**入力の配送は原理的に主張できない** —
T5 の存在理由である。

テスト側は `System.Windows.Automation` (参照ベースの UIA クライアント) を使う。
**ライブラリの手書き interop とは独立実装**になるため相互に検算が効く
(T3 は逆に Core 越しに UIA を触る。揃えないことに意味がある)。

サンプルホストを子プロセスで起動し、`--pick-at x,y` で「カーソルはここに在る」と思わせて
ホバー捕捉を起こす。担当は**ウィンドウを画面に出さないと再現しないもの**で、
T1 で見られるものは置かない:

| 検査 | ここでしか見られないもの |
|---|---|
| `TreeRealisationTests` | 行のコントロールが生成されるのを待つ経路 (仮想化) |
| `PublishedResourceTests` / `HostPublishedResourceTests` | 発行レイアウトでのリソース解決 (前者はピッカーの窓、後者はホストの MainWindow)。`.pri` / サテライトは**発行してからでないと落ちない**。`aot` ジョブが `publish/` を作り、発行物そのものが検査対象になる |
| `OverlayTests` / `OverlayShadowTests` | 実ウィンドウの数・矩形・前後関係 |
| `TreePresentationTests` / `CommitTests` / `SplitterTests` / `ConditionPaneTests` / `WinFormsPickerTests` | 画面に出さないと成立しない表示と、**トリガーファイルに入るところまで** |
| `PickerStaysResponsiveTests` | 応答しない対象アプリの前で UI が凍らないこと。**UI の経路が UIA の経路を待たない**という性質は、T1 の fake View には 2 つを分ける実体が無いので見られない |

**T4 が固定するハーネスの規律** (どれも破ると「静かに間違う」か「原因を名指ししない赤」になる):

1. **DPI 認識はモジュール初期化子 (`TestProcessDpi`) で何よりも先に宣言する** (T3 と共通)。
   UIA に触れた瞬間にプロセスの DPI 認識は `System` に固定され、**二度と変えられない**。
   最初のテスト任せにすると、座標を使わないテストが先に走った実行だけ座標系の全件が落ちる —
   実行順に依存する赤になる。
2. **割り付けは `DesktopLayout` の 1 箇所で決める。**対象アプリとホストの位置が別々の場所に
   書かれていると、片方を動かしたときにもう片方が黙って重なる。画面が狭くて成立しないときは、
   個々のテストではなく割り付けが必要な幅を px で示して落ちる (§6)。
3. **ホストの窓は出た瞬間に退かす。**窓はカスケード位置で開くので「右下は空いている」という
   前提は成立しない。覆われるとピッカーは自プロセスを掴んで捕捉を飛ばし、
   「同じ場所は再捕捉しない」により**二度と捕捉しない** — 症状は原因を言わないタイムアウトになる。
   退かしは競争であって構造的な保証ではないが、負けると
   `RequireThePickPointsAreNotCoveredByTheHost` が**どの窓がどの矩形で覆っているか**を
   名指しして落ちる。**落ちる側に倒れる競争**である。
4. **真偽の根拠は画面の文字列ではなくトリガーファイルに置く。**「追加しました」と出ていることと
   追加されていることは別である。ファイル側では `Id` / `ProcessName` / 経路末端の
   `AutomationId` まで見る — 「1 件入った」だけだと別の要素の定義が入っても通る。
5. **トリガーファイルは `PickerHostProcess` が必ず差し替える。**既定は `%LOCALAPPDATA%` の
   実ファイルで、渡し忘れると自動テストが開発機のトリガーを書き換える。
6. **表示カルチャは `--culture en-US` で固定する。**固定しないとホストは OS の表示言語に従い、
   開発機 (ja) と CI (en) で同じ assert が別の文字列と比べられる。
7. **塞がれた対象アプリを見るテストでは、探針の半分が検査対象と一緒に詰まる。**
   `RootElement` の子を列挙する観測 (`PickerWindow()` / `Overlays()` / `FromPoint` /
   `Diagnostics()`) は、塞がれた窓のプロパティを読みに行って一緒に止まる —
   pid で絞っていても、絞る前に読むので効かない。**塞ぐ前に HWND と行を掴んでおき、
   塞ぎ中は `FromHandle` と `GetWindowRect` だけで観測する。**守らないと、探針が詰まったことを
   「ピッカーが凍った」と読む — §4 と同じ円環が 1 層上で起きる。あわせて、先に送った `ping` が
   塞ぎのあいだ返らないことを確かめる — 相手が本当に塞がっていなければ
   「他方が動き続けた」は何も言っていない。
8. **オーバーレイのクラス名は完全一致で絞る。**枠のクラス名はアイコンのクラス名の接頭辞なので、
   前方一致にすると枠を数えるつもりでアイコンまで数える。枠とアイコンは別々に数える —
   1 つにまとめると「2 つ在る」がピッカー 2 枚なのか枠 + アイコンなのか区別できなくなる。
9. **表示域の広さを前提にするテストは `DesktopLayout.NarrowHost` を渡す。**3 の退かしは
   **寸法も合わせる** (`MoveTo` は `SWP_NOSIZE` を渡していない) ので、窓の幅は
   `DesktopLayout.Host` の幅 = 画面の広さからの引き算である。**窓の既定サイズは
   ここでは観測できない** — 退かされた時点で上書きされる。したがって「内容が表示域に
   収まるかどうか」を見るテストは、既定のままだと機械ごとに結果が変わる。
   実例: 3840×2160 / 175% では窓が 3436×2060 になり、`ConditionPaneTests` の条件欄が
   1550px 取れて最広行 (724px を 175% にした 1267px) が収まってしまう。本文は
   「横=False (見えている割合 100%)」— **はみ出しそのものが起きていない**という形になり、
   **窓の数字が画面の解像度に見えるので原因を取り違えやすい** (実際には 404px 引いた値)。
   1100px 固定なら、**表示スケールが上がるほど内容だけが大きくなる** (窓は物理ピクセル固定)
   ので、はみ出しはどの機械でも成立する。

### T5 — 合成入力で最下層から駆動する層

**低レベルフックとヒットテストは、実際に入力を起こさないと通らない。**UIA のコントロールパターンは
`Invoke` / `Select` を要素へ直接届けるので、`WH_KEYBOARD_LL` も `WM_NCHITTEST` も一度も通らない —
T4 がここへ来られない理由である。

`SendInput` は最下層に入り、ハードウェア入力と同じコードが処理する。物理入力と違うのは 3 点だけで、
いずれも書き出せる: **注入ビットが立つ / UIPI (より高い整合性レベルへは撃てない) /
デバイスとドライバ層を通らない**。だから**人の確認は消えず、補助として残る**。
政策・解禁条件・K/M の記号は §3 が正である。

### T6 — 手動チェックリスト

残るのは物理入力そのものの差と、見た目の最終判断 → docs/MANUAL-CHECKS.md。

## §2 横断ルール

1. **検出力を示せないテストは書かない。**入れる前に意図的な退行で実際に落とし、
   落ちなければ入れない (入れなかった実例は §3 の M1/M2)。退行は「機能を壊す」ではなく
   「**そのテストが主張していることだけ**を壊す」形にする — 機能ごと壊すと、
   狙いと無関係な理由で赤くなり、切り分けの証明にならない。退行を入れたら
   **ビルドの成否を確かめてから走らせる** — 退行がコンパイルエラーになる形だと、
   `--no-build` のテストは古いバイナリで緑になる。
2. **ネガティブコントロール必須。**T3/T4/T5 の各シナリオには「わざと壊した条件で確実に失敗する」
   対を用意する。前提が崩れたときは、時間切れではなく**理由の付いた失敗**で落ちること
   (塞ぎが効いていなければ「対象アプリは 15ms で応答しました」と言って落ちる、の形)。
   **lint 自身もこの規律の対象である** (§3)。
3. **「どの表にも載っていないから緑」の罠。**対応表や列挙で塞ぐ検査は、載っていないものを
   検査しない — そして載っていないものは赤くならない。だから**被覆そのものを固定する検査を
   並べる**: DPI 宣言はどのホストも 2 つの経路のどちらかの表に載っていること自体を固定する /
   XML doc を配るアセンブリが 1 つ残らず検査対象の表に載っていることを固定する /
   「サンプルホスト 3 つ」と配るなら 3 つとも CI が publish していること。
4. **緑は証明ではない。**連続で通ったことは「たまたま通った」と区別できない。
   不安定なテストは「直った」と書かず、名前と落ち方を §5 に記録して追う。
   落ちたら**本文を取る** — 要約行だけを拾う形で反復実行しない (`-v q` を付けない)。
   実 UIA のテストは「落ちた」だけでは何も分からない。
5. **待つ条件は**やりたいこと**で書く。**近いものを代用すると、近いぶんだけ通ってしまう
   (「窓が現れた」は「退かし終えた」ではない。「文字列が非空」は「確定した」ではない)。
   同様に、**弱い assert は偽の緑**である — 「何かが変わった」は「正しく変わった」を言わない。
   「無い」を既定値 (空矩形) に潰して比較すると、読めなかっただけで「変わった」が成立する。
6. **スキップは「まだ書いていない」と区別がつかない。**環境や実装の能力差で見られないものは、
   理由付きスキップ (`Assert.SkipUnless`) にするか、**「出ないこと」自体を assert する** —
   後者は製品を守らないが、出るようになった日にテストが落ちて教えてくれる。
7. **assert は「退行しても同じ症状が出る軸」を避けて置く。**ショーケース検査
   (T4 の `MonitorShowcaseTests` / `CompositeShowcaseTests`) の実例 — テストを弱める前にここを読むこと:
   - 発火は **`FIRED` 行の id と新値まで**突き合わせる。行数だけを数えると、
     解決の通知が来ただけで緑になる
   - 解決状態は**「解決」「未解決」の両方向**を見る。「解決」だけだと、
     一度解決したきり何も追わなくなった監視でも緑になる
   - 監視中の録り直しの真偽は「エラー行が無いこと」ではなく**「録り直したあとも鳴ること」**に置く。
     `RemoveAsync` → `AddAsync` の順に依存しており、逆順だと `AddAsync` が必ず投げるのに、
     投げっぱなしの非同期なので画面には何も出ずログ行が 1 本出るだけ —
     登録に失敗するとトリガーは消えたままになる
   - 監視中の削除は**「残したほうが鳴り続けること」が本体**。「消したほうが鳴らない」だけでは、
     監視ごと止まった場合と区別がつかない。2 件は**同じ要素**に立てる (id だけ違う) —
     別々の要素にするより厳しい
   - 複合条件は**「片方だけでは鳴らない」(発火行の不在を待ち切る) がいちばん大事**。
     「両方満たしたら鳴った」だけなら、条件を無視して鳴っているだけかもしれない
   - **「無いこと」(他ホストに監視 UI が無い等) は自動で見るほうが確実。**
     人は「在るはずのものが無い」には気づくが、その逆は見落とす

## §3 合成入力の政策

規則は 2 本ある。**入力の合成は「入力スタックのどこに入るか」で割る**:

| API | どこに入るか | 判定 |
|---|---|---|
| ウィンドウのキューへ直接入れる 2 つ (`PostMessage` / `SendMessage`) + 非推奨の綴り 2 つ (`keybd_event` / `mouse_event`) | **迂回する。**ヒットテスト・フォーカス判定・低レベルフック・DPI 仮想化を一切通らない | **`tests/**` 全体で全面禁止** (T5 も例外ではない)。緑になっても配送について何も言えない |
| `SendInput` | **最下層に入る。**ハードウェア入力と同じコードが処理する | **`tests/UiaTrigger.Input.Tests` のみ許可。**他では禁止 |

CI の `lint` ジョブはこの 2 本に対応する 2 ステップである。

- **禁止 4 語は文字列として禁止** — テストのコメントに書くだけでも落ちる。不便だが、
  そのおかげで綴りが混入しない。理由の説明はこの文書 (§4) に置き、
  **lint の失敗メッセージとテストは節番号でここを参照する**。
- **`SendInput` の除外はディレクトリ名ではなくパス正規表現で書く**
  (`[\\/]UiaTrigger\.Input\.Tests[\\/]`)。同名のファイルが他所に置かれても免除しないためで、
  区切り文字は両方見る。
- **lint 自身にネガティブコントロールを掛ける** (§2 の規律は lint にも掛かる。とくに除外は、
  広すぎると永久に緑で何も意味しない)。探りはリポジトリの**外** (`%TEMP%` に `tests/` の木を偽装)
  に置く — 中に置くと禁止語を禁止された場所へ持ち込むことになる。確かめるのは 3 件:
  `SendInput` を T5 の外に置くと (2) が赤 / 中に置くと (2) が緑 (免除が効く) /
  迂回系の 1 語を T5 の中に置くと (1) が赤 (T5 も例外ではない)。

### 解禁の 4 条件 (満たせないものは T5 へ持ち込まない)

1. **円環を作らない。**撃つ前に「狙い」(座標とフォーカス) を**別実装の情報源**で検算する。
   通らなければ「入力が届かなかった」ではなく「**ハーネスが狙いを立てられなかった**」として落とす。
   撃てなかったことと届かなかったことも分ける — `SendInput` の受け付け本数が期待と違えば
   その場で落ちる。
2. **ネガティブコントロール。**「OFF にして撃ったら動かなかった」だけでは
   「端に居て動きようがなかった」と区別できないので、**OFF にする前に同じキーで実際に動くこと**を
   確かめてから OFF にする。
3. **人の確認を消さない。**合成入力と物理入力の差 3 点 (注入ビット / UIPI / デバイスとドライバ層)
   は潰せないので、docs/MANUAL-CHECKS.md の該当項目は補助として残す。
4. **`HookProc` が入力の出どころで分岐しないこと**を不変条件で先に固定する (`HookPolicyTests` / T1)。
   合成した入力には例外なく注入ビットが立つ (実測: キー 2/2・マウス 1/1) ので、ここで分岐すると
   T5 と物理入力は必ず別の経路を通る — 注入だけを通す向きなら **T5 は緑のまま実機が死ぬ**。
   検査は**定数名 (`LLKHF_INJECTED`) で探さない** — 生成されていなければ空振りして緑になる。
   識別子 `flags` が本体に現れないことを見て、不在を主張する前に「切り出せたこと」と
   `->vkCode` を実際に読めていることを assert する。

### SendInput の入力デスクトップ要件

`SendInput` は呼び出しスレッドが**入力デスクトップ**に居ることを要求する。
撃つ前に `OpenInputDesktop` で確かめる。hosted runner の対話セッションでも成立することは
実測済みだが、実行環境が変わったとき最初に疑うのはここである。
`INPUT` 共用体は使わなくても `MOUSEINPUT` を含めて定義する — キーボードのぶんだけ書くと
64bit で `cbSize` が 40 ではなく 32 になり、`SendInput` は**1 本も入れずに 0 を返す** —
「届かなかった」に見える形でハーネスが壊れる。カーソル位置は全テストで保存・復帰する
(`CursorGuard`)。

**捕捉 (ホバー滞留) には合成入力を使わない。**`--pick-at` / `FixedCursorSource` のまま —
座標に依存する合成入力を捕捉に使うことが、まさに §4 の円環の形だからである。

**T5 の定番の失敗形: 端に居るものに、端へ向かう操作をして、効かないのを不具合と読む。**
捕捉直後の位置は重なりスタックの終端に居る (→ は clamp されて何もしない)。
クリックで置いたキャレットは行末に居る (→ は動かない)。症状はどちらも「動かない」で、
フックが死んでいるときと**まったく同じ赤**である。assert を書く前に、テスト 1 件ごとに測ること。

### K / M の記号 (この節が正。K4 は欠番)

| 記号 | 内容 | 検査 |

## §4 検証哲学

マウスホイールバグの記録。この文書の戦略 (§1〜§3) は、この事例から直接導かれている。
**CI の lint の失敗メッセージはこの節を名指しする。**

**症状**: ピッカーの TreeView / ListView 上でホイールが効かない。キーボードでは動く。

**真の原因**: App に `app.manifest` が無く、プロセスが DPI 非認識で動作していた。
unpackaged な WinUI 3 アプリでこれが無いと Windows が座標を仮想化する。
`WM_MOUSEWHEEL` はフォーカスウィンドウにスクリーン座標で送られ、WinUI3 が座標をヒットテストして
対象要素へルーティングするため、座標系がずれるとヒットテストがコンテンツ外に落ちてイベントが
破棄される。キーボード入力はヒットテストが不要なので影響を受けない — これが症状の正体だった。
実機は RDP セッションの 4K / 175% スケール環境である。

**修正**: `app.manifest` を追加 (`dpiAware=true/pm`, `dpiAwareness=PerMonitorV2`)。

**なぜ長期化したか**:

- **擬似入力による自動テストが誤った結論を導いた。**「MainWindow でも `PointerWheelChanged` が
  発火しない」という観測は誤りで、実機の物理ホイールでは正常に発火していた。
  この誤った前提が「WinUI3 が `WM_MOUSEWHEEL` を無視する」説を生んだ。
- 切り分けは実機 + 物理入力 + ログで行う必要があった。
- 途中、フックが返す**物理座標**と `GetWindowRect` の**論理座標**を比較して誤判定しかけた。
  **この座標系の不一致自体が DPI 非認識の証拠**であり、真因への手がかりだった。

T2 (§1) はこの事例を初日に検出するために設計されている。

### 教訓を精密にする — 真の失敗は「合成入力を使ったこと」ではなかった

この記録からは「合成入力を全面禁止」という 1 本の規則を導きたくなるが、元の記録を読むと
そうではない。**この失敗は偽陽性 (false green) ではなく偽陰性である。**「発火しない」と観測して、
実機では発火していた。「合成入力は緑を信用できない」というよくある形ですらなかった。
そして 3 つ目の教訓が原因をそのまま書いている — フックの物理座標と `GetWindowRect` の
論理座標を比較していた。

→ **真の失敗は円環である。座標に依存する合成入力で、座標系そのものの不具合を診断した。**
ハーネスの座標の前提が、まさに検査対象に汚染されていた。これは §1 冒頭の教訓 (b)
「検証ハーネス自身を検証する」の具体例であって、API の選択の問題ではなかった。

だから規則は「入力スタックのどこに入るか」で 2 本に割れている (§3):

- ウィンドウのキューへ**直接**メッセージを入れる経路は**全面禁止のまま**。ヒットテストも
  フォーカス判定も低レベルフックも通らないので、緑になっても配送について何も言えない。
  **この事例で本当に効いていた禁止はこちら側である。**
- `SendInput` は**最下層に入る**。同じ `WM_MOUSEWHEEL` の配送であっても、こちらは DPI 仮想化を
  含む実際の経路を通る。**円環を作らない範囲で**解禁されている。

> **ホイールはそれでも人が一次の網である。**真因が DPI 宣言だったので、
> **100% スケールで緑でも 175% を保証しない**。不具合が顕在化した環境そのものが条件であり、
> 自動テストは「配送が完全に死んだ」しか捕まえない。docs/MANUAL-CHECKS.md §1 を弱く見せないために
> T5 に入れていない。**この事例そのものは、いまでも自動では捕まらない。**

## §5 既知の不安定テストと未修正の不具合

| # | 層 | テスト | 状態 |
|---|---|---|---|
| 1 | T5 | `TargetInputTests.WhileThePickerHooksTheKeyboard_OtherAppsStillReceiveArrows` | 全体実行でまれに落ちる。原因未特定 |
| 2 | T1 | `TriggerMonitorPollingTests.Polling_DoesNotDriveResolution` | ビルド直後の 1 回目だけ落ちることがある。見立てはあるが未確認 |
| 3 | T3 | `UnresponsiveTargetTests.AfterAnUnresponsiveSpell_TheAppsOwnTriggerResolvesAgain` | **本物の未修正不具合。**CI ランナーでだけ落ちる |
| 4 | T4 | ランナーで**どれか 1 件**が「ホストの窓が pick 点を覆う」で落ちる | 落ちる顔ぶれは回ごとに違うが、**矩形も pick 点も毎回同じ**。余裕が 4px しかない |

**(1)** 全体実行 (7 件) でまれに落ちる (実測 6 回中 1 回)。単体実行・`OverlayClickTests` との
2 件組・ランナーでの全体実行では再現していない。**落ちたときの本文が取れていない** —
`dotnet test` に `-v q` を付けていると `[FAIL]` の行しか出ない。**次に落ちたらまず本文を取ること。**
このテストは 3 か所で落ちうり、どこで落ちたかで意味がまったく違う:
「フォーカスの検算」= ハーネスが狙いを立てられなかった (製品ではない) /
「キャレットが行頭」= クリックが別の場所に落ちた /
「← でキャレットが動かない」= **フックがキーを吸った (本物の退行)**。
連続で通っても「直った」とは書かない (§2 の 4)。

**(2)** ビルド直後の全体実行の 1 回目だけ落ちることがある。再実行は緑、
`TriggerMonitorPollingTests` 単体でも緑。見立て (**未確認**): T1 は並列を切っておらず、
ビルド直後は CPU が塞がっているため、`FakeTimeProvider` を進める `AdvanceAndDrain` が
周を出し切らないまま assert に来る。見立てを裏付けずに時計やドレインへ手を入れない —
「落ちなくなった」と「見えなくなった」を区別できない。**次に落ちたら `PollCount` の実測値を
取ること** — 5 未満なら見立てが当たりで、そのとき初めて「T1 にも並列切りを入れる」か
「ドレインを待ち合わせに変える」かの判断になる。

**(3) 本物の未修正不具合である。**CI ランナーでだけ落ちる (開発機では緑)。
`real-uia` は `continue-on-error` なので **CI は止まらない — 緑のチェックだけ見ていると
存在に気づけない**。診断はこう出る:

```
sweeps=1 structureEvents=0 subscriptions=2 pathScoped=True resolved=1/2
```

この 5 つの数字は「トリガー `a` の購読が 0 件」を指している。そうなると戻る道が無い —
**購読が無い → イベントが来ない → 掃引が走らない → 購読が張り直されない**、という閉路である。
例外も通知も出ないまま、そのトリガーは永久に解決しなくなる。根にあるのは `IsSameElement` が
`COMException` (**比較できない**) を「**死んでいる**」と決めつけていることで、
相手が塞がれているだけでも同じ例外が出る。緩和 (張り替えられると分かるまで壊さない /
孤立トリガーの拾い直し / 診断カウンタ) は入っているが、**「購読が失われたら実際に張り直る」の
end-to-end はランナー上の T3 でしか検証されていない** — 開発機では塞がれた相手でも
ウィンドウ解決が成功してしまい、壊れる状況を作れない (実験 3 種とも再現せず)。
残る不明点は「ランナーで実際に落ちたのはどの呼び出しか」であり、分けるには
ランナー上の monitor のログが要る。設計側の記述は docs/DESIGN.md §8。

**(4)** `PickerHostProcess.RequireThePickPointsAreNotCoveredByTheHost` が落とす。
**これは狙いどおりの落ち方である** — ガードが無ければ、ホバー捕捉が起きず
`_lastCapturedPoint` により再捕捉もされないまま「実体化しなかった」という顔の
20 秒タイムアウトになる (§6 と同じ形)。落ちたときの実測値:

```
pick 点 (1670,676) がホストの窓 (234,234)-(1674,987) に覆われています
(class='WinUIDesktopWin32WindowClass')
```

**落ちる顔ぶれは回ごとに違う** (`CompositeShowcaseTests.ABrokenExpression_IsRefusedAndAddsNothing`
と `MonitorShowcaseTests.DeletingOneTriggerWhileMonitoring_LeavesTheOthersRunning` で実測)。
**しかし矩形も pick 点も 2 回とも 1 px 違わず同じである。**窓の出る位置が揺れているのではない。

- **余裕が 4px しかない。**pick 点の x=1670 に対してホストの窓の右端は 1674 である。
  つまり境界の当たり方の問題であり、**どのテストが落ちるかだけが揺れている**。
- 窓の幅は 1440px で、`DesktopLayout.NarrowHost` の 1100px ではない。狭いホストの話ではない。
- 再実行すると緑になる (実測 1 回)。**「直った」とは書かない。**

次に触るときは、揺れを追うのではなく **pick 点と `DesktopLayout` の `Host` 右端・`Gap` を
突き合わせる**こと。4px という数字は、片方をわずかに動かせば消える種類の重なりを指している。

## §6 ローカル実行の注意

- **ビルドはソリューション経由のみ**: `dotnet build UiaTrigger.slnx -c Release`。
  プロジェクト単体の `dotnet build src/<プロジェクト>` は `bin\Debug\...` という**別の出力先**を
  作り、ソリューションビルドの `bin\x64\...` と並存する。T4 の `PickerHostProcess` は
  「いちばん新しい exe」を採るので、単体ビルドの直後から**別レイアウトのホストを黙って
  起動しはじめる**。踏んだら `bin\Debug` (x64 無しの側) を消してソリューションで建て直すこと。
- **T4 の前に前回の窓を掃除する**:

  ```powershell
  Get-Process | Where-Object { $_.Name -like "UiaTrigger*" } | Stop-Process -Force
  ```

  前の実行の窓 (対象アプリ / ホスト / ランナー) が残っていると、**無関係なテストが座標で落ちる** —
  落ちた顔ぶれは実行のたびに変わり、内容は「狙った座標に居るのが対象アプリではない」
  「ホバー捕捉が成立しない」に偏る。**ランナーが緑で手元が赤いときは、まずこれを疑う。**
  落ち方が座標と前提条件の失敗 (ハーネスが「この状態では意味がありません」と言って落ちる形)
  に偏っているのが目印で、assert の中身で落ちているなら別の話である。
- **T4 は画面幅 1,481px 以上が必要** (`NarrowHost` の幅 1100 + 対象アプリ 380 + 1)。
  1600×900 は通る。**1024×768 は原理的に不成立** — 使えるホスト幅 620px ではツリーが約 322px
  になり、「畳んだ 1 行が収まる」下限 346px を割るので、対照 (畳めばスクロール不要) のほうが
  壊れる。**テスト側では直せず、画面のほうを変える。**CI の `picker-ui` は
  `Set-DisplayResolution` (ServerCore モジュール) で 1920×1080 にする。読み取りは
  `GetSystemMetrics` — ランナーの仮想ディスプレイでは
  `EnumDisplaySettings(ENUM_CURRENT_SETTINGS)` が 0x0 を返し、現在値を答えない。
  画面が足りなければ `RequireTheNarrowHostFitsOnThisScreen` が必要な幅を px で名指しして落ちる。
- **`dotnet test UiaTrigger.slnx` はテストプロジェクトを並列に走らせる。**T3 / T4 / T5 は
  窓・座標・実入力を取り合うので、全体実行では**互いを落とす** (実測: 並列で 5 件赤 →
  同じビルドを 1 プロジェクトずつ直列で回すと T5 7/7・T3 71/71 が緑)。CI がジョブを
  分けているのは同じ理由である。層をまたいで確かめるときは 1 プロジェクトずつ回すこと。
- **`gh run watch --exit-status` の終了コードを信用しない。**赤い実行に対して 0 を返した実績がある。
  **判定は `gh run list` / `gh run view` で取ること。**
- 反復実行は毎回全出力を残す形で回す (§2 の 4)。失敗の本文を捨てる形で回すと、
  落ちた 1 回から何も学べない。
